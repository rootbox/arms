> 이 문서는 앱 개발을 일단락하며 정리한 **최종본**입니다. 무엇을 만들었고, 왜 그렇게 만들었고,
> 실전에서 무엇이 깨졌고 어떻게 고쳤는지를 한 곳에 모았습니다.
> 기준 시점: **2026-09-20 / v0.7.0-rc15 (versionCode 20, 정식 발행은 실차 검증 후)**

---

## 1. 개요

**운전 중에 듣고 싶은 것을 듣기 위한 앱.** 두 가지를 한 앱에서 다룹니다.

1. **실시간 라디오** — KBS Cool FM, SBS 파워FM, 24/7 K-POP 채널
2. **내 NAS의 음악** — 집에 있는 Synology NAS(Audio Station)에 쌓아둔 음원

둘 다 **Android Auto**에서 쓰는 것이 목적이고, 폰 화면은 그 보조입니다. 스트리밍 구독 없이
내가 가진 음원을 차에서 듣고 싶다는 것이 NAS 기능의 출발점이었습니다.

내부 코드명은 `ARMS`(Automobile Radio & Music Streaming), 표시 이름은 `Simple Radio`입니다.
패키지·클래스 이름에는 ARMS가 그대로 남아 있습니다.

## 3. 아키텍처

```
app/                    Compose UI + 미디어 서비스(차량·블루투스·폰 공용)
├── MainActivity.kt              폰 화면 전체 (탭, 미니플레이어, 전체화면 플레이어)
├── SessionAudioPlayer.kt        폰 화면 → 서비스 세션 컨트롤러 (AudioPlayer 구현)
├── ARMSMediaLibraryService.kt   MediaLibraryService (브라우징 + 재생 + 세션). 플레이어는 여기 하나뿐
├── UpdateChecker.kt             GitHub Releases 기반 인앱 업데이트
├── auto/                        차량 전용 (MediaId 스킴, NAS 브라우즈 트리)
└── ui/nas|theme/                NAS 화면들, 디자인 토큰

core/model      순수 데이터 모델 (Station, NasAlbum, NasSong, NasTrack, NasPlaylist)
core/network    외부 API (JVM 모듈): RadioApi(ICY·Deezer 포함), SynologyMusicApi, NetworkClient
core/playback   AudioPlayer 인터페이스 + QueueTrack (플랫폼 독립, 데스크톱과 공유)
core/data       저장소 계층: Room DB 2개, 암호화 자격증명, 재생 상태, 채널 아트
desktop/        macOS/Windows 앱 (Compose for Desktop + VLCJ) — docs/DESKTOP_PORT_PLAN.md
```

### 플레이어는 하나다 (0.7.0에서 바뀐 것 — 중요)

0.6.x까지는 폰 화면이 자체 ExoPlayer(`core/media`)로, 차량은 서비스의 ExoPlayer로 **따로**
재생했습니다. 그 분리는 Android Auto에서는 장점이었지만(연결 해제 격리), **블루투스만으로
쓰는 차량에서는 근본 원인**이었습니다 — 폰 재생에 MediaSession이 없어 차량이 곡 정보를 받지도,
이전/다음 버튼을 보내지도 못했습니다(§6.12). 0.7.0부터 폰 화면은 `SessionAudioPlayer`로 서비스
세션의 컨트롤러가 되고, 라디오/NAS를 **mediaId로 요청**해 차량과 같은 경로를 탑니다.
서비스는 재생을 차량이 시작했는지(`playbackInitiatedByCar`)를 기억해, Android Auto 해제 시
정지·포커스 재개 포기·낡은 큐 폐기를 차량 시작 재생에만 적용합니다(`BluetoothModePolicy`).

### 저장소가 둘인 이유

- `arms_database` (Room v1) — 라디오 방송국
- `arms_playlists` (Room v1) — NAS 플레이리스트

플레이리스트를 기존 DB에 테이블로 추가하지 않고 **별도 DB로 분리**했습니다. 기존 DB가
`exportSchema=false`라 스키마 검증이 불가능한 상태였고, Room은 마이그레이션 후 스키마가
한 글자만 달라도 **실행 즉시 크래시**시킵니다. GitHub Releases로 직접 배포하는 구조라
되돌리기가 어려워, 마이그레이션 자체를 발생시키지 않는 쪽을 택했습니다.
새 DB는 `exportSchema=true`로 시작해 스키마를 커밋합니다.

## 4. 기능

### 라디오
- KBS Cool FM(89.1) / SBS 파워FM(107.7) / K-POP 24/7 (LISTEN.moe)
- **K-POP 발라드 24/7** (sCast.kr Naya Ballad → laut.fm Kpop Love 폴백) / **K-POP 2세대 히트 24/7**
  (Zeno.FM Kpop Rewind). 곡 정보는 스트림의 ICY 메타데이터, 커버는 Deezer 엄격 일치 → 없으면
  번들 채널 아트. "80/90년대 가요" 전용 공개 스트림은 2026-09 실측에서 없었음.
- 실제 편성 정보와 프로필·커버 이미지를 갱신 (차량 8초 / 폰 30초 주기). 커버를 못 받으면 백오프로 다시 시도
- 즐겨찾기, 마지막 채널 자동 재개
- 이전/다음 버튼 = **채널 전환** (실시간 방송엔 "다음 트랙"이 없으므로)
- SBS 전용 라우드니스 보정 (+10dB) — 원본 스트림이 상대적으로 조용함

### NAS 음악
- 아티스트 → 앨범 → 곡 탐색, 앨범/아티스트 검색
- 플레이리스트 생성·담기·이름변경·삭제
- 앨범 아트, 아티스트/앨범 메타데이터
- 셔플 / 반복(끄기·전체·한 곡), 진행바 탐색
- **이어듣기** — 앱을 껐다 켜도 마지막 트랙·재생 위치에서 재개

### 블루투스 모드 (Android Auto 없이)
- 폰에서 재생을 시작하면 세션을 통해 차량이 곡 정보를 받고 이전/다음(=채널 전환) 버튼이 동작
- 차량 화면 표시: 지상파는 "SBS 파워FM - 황제성의 황제파워"(채널 - 프로그램), 스트리밍은 곡 제목 / 채널명
- 블루투스 끊김: 라디오 정지(큐 비움) / NAS 일시정지. 재연결·시동 시 헤드유닛 PLAY로 재개
  (`MediaButtonReceiver` + `onPlaybackResumption`, 프로세스가 죽어 있어도 동작)
- 잠금화면/알림 미디어 컨트롤, 앱을 닫아도 재생 유지
- 계획·검증 기록: `docs/BLUETOOTH_MODE_PLAN.md`

### 차량 (Android Auto)
- 브라우징 루트: 최근 재생한 앨범 / 플레이리스트 / 아티스트 / 라디오
- 시동을 걸면 마지막에 듣던 것을 자동 재개
- 셔플·반복 커스텀 버튼 (NAS 재생 시에만 노출)
- 차량 연결 해제 시 즉시 정지 + 큐/버퍼 폐기

## 5. 주요 설계 결정

**차량과 폰은 달라도 된다.** 폰은 앨범을 누르면 곡 목록으로 들어가지만, 차량은 앨범을 누르면
바로 재생합니다. 주행 중 조작 횟수를 줄이는 것이 일관성보다 우선입니다.

**차량 브라우징은 네트워크 0을 목표로.** 플레이리스트 목록과 최근 앨범은 곡 정보까지
로컬에 저장해두고 DB만 읽어 그립니다. 터널이나 NAS 장애 상황에서도 목록은 뜨고, 실제로
누른 순간에 처음 네트워크를 씁니다.

**`ActivePlayback`으로 재생 종류를 하나로 다룬다.** 라디오/NAS 분기가 UI 곳곳에 흩어지면
반드시 어긋나므로, sealed class 하나로 제목·부제·동작을 결정합니다.

**재생 종류 판별은 mediaId 접두사로.** 별도 플래그를 두면 갱신 지점(재생 시작/에러 재시도/
자동 재개/트랙 전환)이 여러 곳이라 언젠가 어긋납니다.

**`NasMusicRepository`의 mutex는 재진입 불가.** public 함수끼리 서로 호출하면 즉시 데드락입니다.
내부 헬퍼(`songs()`, `session()`)를 직접 부르고, 헬퍼에는 "호출부가 락을 보유한다"는 전제를
주석으로 명시했습니다.

**플레이리스트 순서는 요청 순서를 보존.** 캐시를 `filter`로 거르면 NAS가 준 순서로 나와
사용자가 담은 순서와 달라집니다. `associateBy` 인덱스로 요청 순서를 유지하고 단위 테스트로 고정했습니다.

## 6. 실전에서 배운 것 (버그와 근본 원인)

이 앱에서 가장 값진 부분입니다. 대부분 **실제 주행 로그를 분석해서** 찾았습니다.

### 6.1 Play Protect가 "유해한 앱"으로 차단
릴리즈 워크플로가 `assembleDebug`를 배포하고 있었습니다. 디버그 APK는 `debuggable=true`에
디버그 키 서명이고, CI가 매 빌드 디버그 키를 새로 만들어 서명이 흔들렸습니다.
→ **정식 릴리즈 키로 서명한 `assembleRelease` 배포로 전환.** 키는 사용자가 소유하고
GitHub Secrets로 CI에 주입합니다.

### 6.2 앱 실행마다 NAS "새 로그인" 알림
실행당 로그인이 **2회** 나가고 있었습니다. ①시작 시 앨범 목록 로드 ②자동 이어듣기의 재생
경로가 **무조건 `forceFresh=true`**로 방금 받은 세션을 무시하고 또 로그인.
→ **sid를 암호화 저장소에 영속화**하고, 인증 오류(105/106/107/119, 401/403)를 네트워크 오류와
구분해 **그때만** 재로그인. 평상시 로그인 0회.

### 6.3 차량 연결이 끊겨도 재생이 계속됨
정지 조건이 "연결된 컨트롤러가 하나도 없을 때"였는데, **미디어 알림 컨트롤러가 세션에 항상
붙어 있어** 그 조건이 참이 되지 않았습니다. 고친 뒤에도 문제가 남았는데, **Android Auto는
차량 링크가 끊겨도 우리 서비스 바인딩을 유지**해서 `onDisconnected`가 아예 오지 않았습니다.
→ **`CarConnection` API로 차량 연결 상태를 직접 관찰.** 추가로 재연결 시점에도 낡은 큐가
남아 있으면 폐기하는 안전망을 뒀습니다(이탈을 놓쳐도 과거 오디오가 재생되지 않도록).

### 6.4 음성인식 후 라디오가 되다 안 되다
재생이 멈추면 미디어 포그라운드 서비스가 내려가고, **그 상태(백그라운드)의 오디오 포커스
요청을 시스템이 무시**합니다(`AudioHardening focus request ignored`). 2초 간격 재시도가
하루 63건 거부되며 알림만 125건 쌓였습니다.
→ **3회 실패하면 포기.** 그리고 차량 연결이 확인되지 않으면 시도하지 않습니다.
참고로 내비 길안내는 `LOSS_TR_CAN_DUCK`(볼륨만 낮춤)이라 원래 문제가 없었고, 문제는
상대 앱이 **영구 포커스**를 가져갈 때만 발생합니다.

### 6.5 NAS 곡에 앨범 아트가 없음
NAS 재생 경로가 MediaItem에 제목만 넣고 있었습니다.
→ Synology `cover.cgi`로 **스트림 URL과 같은 sid로 서명된 커버 URL**을 만들어 폰·차량 양쪽에
실었습니다. 아티스트/앨범 메타데이터도 이때 함께 채웠습니다.

### 6.6 라이브 스트림이 과거 구간부터 재생됨
자동 재개에서 `startPositionMs=0`으로 고정하면, DVR 버퍼를 제공하는 방송사 스트림은
**버퍼 맨 앞부터** 재생됩니다.
→ `C.TIME_UNSET`으로 두면 라이브 최신 지점부터 시작합니다.

### 6.7 차량에서 셔플/반복이 안 보임
Android Auto는 셔플·반복을 기본 버튼으로 그리지 않고 **커스텀 액션으로 올린 것만** 표시합니다.
→ `setCustomLayout`으로 버튼을 올렸습니다. 이때 `ForwardingPlayer`의 리스너 래퍼가
**명시한 콜백만 전달**하는 구조라 셔플/반복 변경이 세션에 전달되지 않던 결함도 함께 고쳤습니다.

### 6.8 APK가 192MB로 부풀었던 일
테스트 전용 의존성이 `implementation`으로 들어가 있었습니다. 의존성 스코프는 눈에 잘 띄지 않으니
용량이 튀면 먼저 의심할 곳입니다.

### 6.9 커버가 한 번 실패하면 회색으로 남음 (2026-09, 장기 실사용 보고)
편성/곡 정보가 그대로면 갱신 루프가 그대로 return해서, **한 번 실패한 커버는 편성이나 곡이
바뀔 때까지 다시 시도되지 않았습니다.** 게다가 편성 조회가 잠깐 실패하면 "정보 없음"이라는
정상 값처럼 돌아와 "정보가 바뀌었다"로 판정되고 멀쩡한 커버까지 지웠습니다. 커버 다운로드도
상태코드·Content-Type 검사 없이 본문을 .jpg로 저장해 오류 페이지가 이미지가 되기도 했습니다.
→ 정보가 그대로여도 커버만 비면 **백오프(8s→최대 2분)로 커버만 재시도**, 조회 실패는 null로
돌려 기존 값 유지, 다운로드는 OkHttp + 상태코드·`image/*`·디코딩 검사. 폰은 30초 주기 갱신을
추가하고 `RetryingAsyncImage`로 실패 시 재시도. 실기기에서 "이미지만 차단 → 네트워크 복구
→ 25초 내 자동 복구"를 확인했습니다.

### 6.10 K-POP 커버가 대부분 비어 있던 이유
SSE 메타데이터에는 커버가 없어 곡 제목으로 GraphQL을 **검색**해 커버를 찾았는데, 실측에서
유명곡 6곡 중 5곡을 못 찾았습니다(검색이 제목을 잘 매칭하지 못함). LISTEN.moe **게이트웨이**
(`wss://listen.moe/kpop/gateway_v2`, 공식 3rd-party API)는 같은 곡의 곡·아티스트·커버를 한 번에
줍니다. → 게이트웨이를 1차로 쓰고(접속 직후 첫 TRACK_UPDATE만 받고 종료), 옛 경로는 폴백.

### 6.12 블루투스만 쓰는 차량에서 곡 정보·버튼·재개가 전부 안 되던 이유 (2026-09-20)
증상 넷(정보 미노출·이전/다음 무반응·끊겨도 계속 재생·재연결 시 미재개)의 원인은 하나였습니다.
**폰 화면의 재생이 MediaSession 없는 자체 ExoPlayer로 돌아** OS와 차량이 그 재생을 볼 수 없었던
것(`dumpsys media_session`에 우리 세션이 없고 "Audio playback" 목록에만 등장). → 폰 재생을 서비스
세션으로 통합(§3). 함께 필요했던 조각: `MediaButtonReceiver` 선언(프로세스가 죽은 뒤 PLAY를 받아
서비스를 깨움), `setHandleAudioBecomingNoisy`, 컨트롤러가 요청 목록 기준으로 startIndex를 검증해
던지는 `IllegalSeekPositionException`(시작 위치는 요청 메타데이터로 보내 서비스가 결정).

### 6.13 모듈을 지웠더니 라디오가 안 나옴 — 런타임 전이 의존성
`core/media`를 지우자 그 모듈이 implementation으로 물고 있던 `media3-exoplayer-hls`가 APK에서
함께 빠졌습니다. 앱은 그 모듈을 직접 선언한 적이 없어 **컴파일은 통과**했고, 실행 중 HLS 항목을
setMediaItem하는 순간 `No suitable media source factory found for content type: 2`가 났습니다
(rc4~rc7). dex에서 `HlsMediaSource` 참조 수를 세어 확정했습니다. → 모듈을 지울 땐 그 모듈이
런타임에 전이시키던 의존성을 확인하고, **라디오(HLS)와 스트리밍(MP3) 양쪽을 실기기에서 재생**할 것.

### 6.14 채널 전환이 되돌아오던 레이스
편성 갱신 루프는 조회 시작 때의 항목을 기반으로 `replaceMediaItem`을 했는데, 커버 다운로드(수 초)
뒤 교체 직전에 "채널이 아직 그대로인가"를 다시 보지 않았습니다. 그 사이 버튼으로 채널이 바뀌면
새 항목이 옛 항목으로 덮였습니다. → 교체 직전 재확인 + 현재 항목 기반 교체. 채널 전환도 편성·
커버를 다 받은 뒤가 아니라 **새 URL로 먼저 전환하고 정보는 나중에** 채우도록 바꿨습니다.

### 6.15 스트림에 매달린 로깅 인터셉터
`HttpLoggingInterceptor(Level.BODY)`는 응답 본문을 끝까지 읽어 로그로 남깁니다. 오디오 스트림은
끝이 없어 ICY 메타데이터/생존 확인 요청이 영원히 블록됐습니다(jstack으로 확인). 인터셉터 없는
`OkHttpClient()`로 한 사전 검증은 통과했기에 놓쳤습니다. → 스트림 요청은 로깅을 뗀 전용
클라이언트 + 짧은 타임아웃. **검증은 앱이 실제로 쓰는 클라이언트로.**

### 6.16 LTE에서 K-POP 계열 채널만 수십 초 지연·무음 (2026-09-24, S22)
폰에서 직접 잰 스트림 호스트 응답은 전부 0.4~2.3초로 정상이었습니다. 원인은 앱이 **재생 전에
하는 일**: 최초 탭·오류 재시도·자동 재개 경로가 편성·곡·커버를 직렬로 다 받은 뒤에야 URL을
플레이어에 넘겼고(K-POP은 게이트웨이 대기+폴백으로 최악 86초), 게이트웨이 웹소켓을 `close()`만
해서 **소켓 19개가 누수**돼 이후 호출이 10초 타임아웃에 걸렸으며, 8초마다 스트림 호스트에 새
연결(ICY/웹소켓)을 열어 재생 연결과 경쟁했습니다. Wi-Fi(S25)에선 전부 빨라 드러나지 않았습니다.
→ 모든 시작 경로를 "새 URL로 즉시 재생, 정보는 후속"으로 통일. 발라드/2세대 곡 정보는 **재생
연결의 인밴드 ICY**(`onMetadata`)로 받고 별도 연결을 열지 않음. 웹소켓은 `cancel()`로 확실히
해제 + 결과 20초 캐시. 생존 확인은 병렬·6초 상한·성공만 캐시·앞 후보 확인 즉시 반환.
LTE 실측: 발라드 8→(rc13 예상 4)초, 2세대 7초, K-POP 4~7초, KBS 2초. Zeno가 곡 사이에 보내는
`StreamTitle="-"`는 제목으로 보지 않도록 함. **교훈: 재생 시작 경로에 네트워크 대기를 두지 말 것,
검증은 사용자의 실제 망(LTE)에서 할 것.**

### 6.17 블루투스 실사용 단말(S24) 리그레션에서 잡은 것과 폰 설정 (2026-09-24)
16개 항목 중 UI 동기화 2건이 실패: ① 서비스가 인밴드 채널을 재생 중일 때 앱을 다시 열면
"정보 없음"+회색 커버(세션이 이미 가진 곡 정보를 읽지 않고 다음 곡 변경만 기다림) ② 미디어키
STOP 뒤에도 화면은 "재생 중"(큐가 남아 항목 전환 이벤트가 없음). → 채널 선택 시 세션의 현재
항목이 그 채널이면 곡/커버를 즉시 가져오고, 플레이어가 IDLE이 되면 화면을 내린다(rc14).
신규 설치 폰의 앱 정보에 알림이 "차단됨"이라 POST_NOTIFICATIONS를 선언하고 첫 실행에
요청한다(rc15). 설치 시 옛 디버그 서명 빌드(0.1.0)가 남아 있으면 서명 불일치로 덮어쓰기가
거부되므로 제거 후 설치해야 한다.
**폰 설정(블루투스 모드에 필요)**: 앱 배터리 "제한 없음"(= 도즈 허용목록; 앱의 배너가 요구),
백그라운드 실행 허용, 적응형 배터리 끄기. 삼성은 "제한 없음"인 앱을 절전 대상에서 제외하므로
절전 예외 목록에 따로 넣을 필요가 없다(검색해도 안 나옴). adb로는
`dumpsys deviceidle whitelist +com.arms.androidauto`, `appops set … RUN_ANY_IN_BACKGROUND allow`,
`am set-standby-bucket … active`, `settings put global adaptive_battery_management_enabled 0`.
재시동 시 PLAY는 **마지막으로 소리를 낸 앱**에게 가므로, 하차 직전 다른 음악 앱이 재생 중이면
그 앱이 받는다(삼성 뮤직의 "외부 기기에서 재생 시작 허용" 끄기 권장).
후속 과제: Media3 1.3.1은 일시정지 즉시 포그라운드를 내려 Android 15+에서 백그라운드 재개 시
포커스 실패 여지가 있고 삼성/Android 15 startForeground 크래시 보고가 있음 — 1.6+(일시정지 후
10분 유지)로 업그레이드 검토(API 변경이 있어 회귀 게이트 필요).

### 6.11 SBS 커버가 하루 대부분 비어 있던 이유
편성 소스로 쓰던 `bora/today`는 이름대로 **"보이는 라디오" 편성표**라 영상이 있는 방송만
담겨 있었습니다(어느 날 파워FM은 07-09시·22-23시 두 개뿐). 앱은 그 목록에서 현재 시간대를
못 찾으면 커버를 비웠고, 그래서 황제성 방송처럼 커버가 분명히 있는 시간대에도 회색이었습니다.
→ `play-api/1.0/onair/channel/S07`("지금 방송 중" 프로그램 하나를 직접 제공)를 1차로 쓰고,
보이는 라디오 편성표는 2차, 그래도 이미지가 없으면 SBS가 호스팅하는 파워FM 채널 이미지로
폴백합니다. **외부 API를 쓸 때는 그 API가 무엇의 목록인지 이름과 필드로 먼저 확인할 것.**

확인**하는 것이 유일한 대응입니다. 이 비공식 의존성이 Google Play 등재를 막는 근본 이유이기도 합니다(§9).

## 8. 배포

```
버전 올림 → 커밋 → v<versionCode> 태그 푸시
   → GitHub Actions가 릴리즈 키로 서명한 APK 빌드
   → GitHub Release 발행
   → 앱이 실행 시 최신 릴리즈를 확인하고 업데이트 안내
```

- 서명 정보: 로컬은 `keystore.properties`(깃 제외), CI는 GitHub Secrets
  (`KEYSTORE_BASE64` / `KEYSTORE_PASSWORD` / `KEY_ALIAS` / `KEY_PASSWORD`)
- **키스토어와 비밀번호는 반드시 백업.** 분실하면 같은 키로 업데이트를 만들 수 없어
  기기에서 삭제 후 재설치가 강제됩니다.
- 키가 없는 환경에서는 릴리즈가 미서명으로 빌드되어, 빌드 자체는 통과합니다.

## 9. Google Play 등재 검토 결과 — 등재하지 않음

두 차례 검토했고 결론은 같습니다. 자세한 내용은 [PLAYSTORE_RELEASE_PLAN.md](PLAYSTORE_RELEASE_PLAN.md).

1. **라디오는 공개 배포가 불가능합니다.** 방송사 내부 API로 라이브 스트림을 받아 재생하는
   구조라 제3자 재배포 권한이 없습니다. 개인 사용과 스토어 배포는 다른 문제입니다.
2. **라디오를 빼면 심사자가 앱을 쓸 수 없습니다.** Synology NAS와 계정 없이는 빈 화면뿐이라,
   통과하려면 **데모 모드를 새로 개발**해야 합니다.
3. 그 밖에 `REQUEST_INSTALL_PACKAGES`(인앱 업데이트) 제거, 배터리 최적화 권한 정리,
   Android Auto 별도 품질 심사가 필요합니다.

들이는 비용 대비 대상이 지나치게 좁고, **정작 본인이 매일 쓰는 라디오가 빠진 버전을 따로
관리**해야 합니다. 지금의 GitHub 배포로 충분합니다.

## 10. 의도적으로 하지 않은 것

- **오프라인 캐시** — 모든 NAS 곡은 스트리밍입니다. 터널·음영지역 대비로 가치가 있지만
  다운로드 관리·저장공간 정리가 따라붙습니다.
- **음성 검색** — `onSearch`/`onGetSearchResult` 미구현이라 "헤이 구글, ○○ 틀어줘"가 안 됩니다.
- **곡 단위 검색** — 폰 검색은 아티스트·앨범만 대상입니다.
- **`setFolderType` 대체** — deprecated지만 차량 브라우징 렌더링에 영향을 줄 수 있고
  실차 검증 없이는 확인이 불가능해 그대로 뒀습니다. 경고 2건은 의도된 잔여물입니다.

## 11. 유지보수 메모

**문제가 생기면 로그부터.** 이 앱의 버그 대부분은 추측이 아니라 실제 주행 로그에서 찾았습니다.
```bash
adb logcat -b all -d -v threadtime > log.txt
grep "AudioFocusManager" log.txt          # 포커스 상실/복귀
grep "HardeningEnforcer.*arms" log.txt    # 시스템이 막은 포커스 요청
grep "am_foreground_service_st" log.txt   # 재생 시작/멈춤
grep "CDM_DevicePresence.*gearhead" log.txt  # 차량 연결/해제
grep "notification_enqueue.*arms" log.txt    # 재생 중이면 주기적으로 찍힘
```

**차량 동작은 실차에서만 검증됩니다.** 폰에 설치해 확인할 수 있는 것과 차량에서만 드러나는 것을
구분해야 합니다. 커밋 메시지에 "실차 검증 필요"를 남겨둔 항목들이 그런 경우입니다.

**릴리즈 키가 바뀌면 사용자는 앱을 지우고 다시 설치해야 합니다.** 되돌릴 수 없으니 키 관리가
이 프로젝트에서 가장 사고 나기 쉬운 지점입니다.
