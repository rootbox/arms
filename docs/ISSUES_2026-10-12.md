# 실사용 버그 분석 (2026-10-12, v0.9.0 태블릿 호스트 + SmartThings)

사용자 보고 2건을 기기 없이 코드·라이브러리 바이트코드·드라이버 테스트로 분석. 확정/추정 구분.

## 1. SmartThings에서 전원 켜기가 먹지 않음 (ST 앱은 "연결됨"으로 보임)
**확정된 구조 결함 (둘 중 하나만 걸려도 증상 재현)**
- **드라이버가 실패를 삼키고 성공은 검증하지 않는다.** `handlers.lua send_command`: 200이면 `switch=on`을 낙관 반영하고 끝, 실패(타임아웃·503·504·500)면 로그만 남기고 상태 재조회·이벤트 없음 → ST 스위치는 스피너 뒤 OFF로 원복. 드라이버 타임아웃 5s = 호스트 명령 예산 5s라 호스트의 504는 드라이버에 도달하지 못한다. 온라인 판정은 SSE 연결만 보므로 명령이 전부 실패해도 "연결됨·프리셋·마지막 곡"이 유지된다(관찰과 일치). 재현: 드라이버 단위 테스트(가짜 클라이언트로 타임아웃/503/200-무변화) 4/4 실패 확인.
- **호스트는 아무 일도 안 해도 200을 준다.** `RemoteHostService`의 MediaController는 onCreate에서 한 번만 만들고 `onDisconnected` 처리가 없다. 세션이 끊기면 Media3가 컨트롤러를 자동 release → `setMediaItem/prepare/play`는 "not connected. Ignoring"으로 무시되지만 `play()`는 true를 돌려줘 200. 명령 후 상태 push는 "내용이 바뀔 때만"이라 ST는 낙관 ON으로 남는다. `controller==null`이면 재연결 없이 영구 503.
- **부가:** 제목이 없는 상태에서 `audioTrackData` emit이 "Required field missing: title"로 매번 실패(드라이버가 삼킴).

**이번 사건의 트리거(추정, 로그로 확정 필요)**: 장시간 화면 꺼진 태블릿의 **인바운드 TCP 지연/유실**. 앱에 WakeLock/WifiLock/`setWakeMode`가 전혀 없어 Wi-Fi 절전·CPU suspend 시 허브→태블릿 새 연결(명령)만 5초 안에 실패하고, 이미 열린 SSE와 태블릿→브로커 아웃바운드(폰 리모컨)는 살아 있다. "폰 리모컨으로 켜자 ST도 정상"이 이 가설과 맞는다. 보조 가설: 반쯤 죽은 SSE 소켓이 `maxConnections`(16)를 채워 `503 busy`.

**확정 방법(다음 기회)**: 허브 로그 `edge:drivers:logcat --all` 에서 ON 탭 시 `명령 on 실패: …timeout`(트리거 C) / `HTTP 503 unavailable`(컨트롤러 없음) / `전송 완료`인데 무음(컨트롤러 release). 화면 끄고 2~3시간 뒤 Mac에서 `curl -m 5 -X POST …/command on` 응답 시간.

**수정 방향(우선순위)**
1. 드라이버: 실패 시 `GET /state`로 즉시 원복 + 503/504도 실패로 집계; 성공 시 낙관 반영 대신 1.5초 뒤 상태 재조회로 검증; 타임아웃 8s. (ST 반응 ~1.5s 지연 감수)
2. 호스트: `onDisconnected` → 컨트롤러 백오프 재연결; On 시 `!isConnected`면 503+재연결; 명령 뒤 상태를 무조건 한 번 push; IDLE이면 `setMediaItem(현재/마지막)+prepare+play`(만료 서명 URL 회피).
3. 벽걸이 모드: 로컬 제어 켜짐+충전 중이면 `PARTIAL_WAKE_LOCK`+`WifiLock(FULL_LOW_LATENCY)`, ExoPlayer `setWakeMode(WAKE_MODE_NETWORK)`.
4. SSE: 같은 클라이언트의 기존 스트림 교체(최대 1개), SSE는 동시 연결 상한에서 제외. `audioTrackData`는 제목 없으면 생략.

## 2. 볼륨이 비정상적으로 작게 들림 (30+ 필요 → 앱 재시작 후 8이 같은 크기)
**1순위(모든 관찰과 일치): 오디오 포커스 덕킹(-14dB, ×0.2)이 해제되지 않고 고착.**
- Media3 1.3.1 `AudioFocusManager`: `VOLUME_MULTIPLIER_DUCK=0.2`, 공개 API `player.volume`에는 보이지 않음. 앱은 `handleAudioFocus=true`이고 `player.volume`을 읽거나 복원하는 코드가 없다.
- targetSdk 35에서는 프레임워크가 uid 단위로 AudioTrack에 VolumeShaper(1.0→0.2)를 걸어 덕킹하고, ExoPlayer는 포커스 상태를 유지한 채라 채널 전환(prepare/play)에도 포커스를 재요청하지 않는다 → **채널을 바꿔도 조용함**. 해제는 덕킹 승자의 abandon, 우리가 `stop()`→abandon→재요청, 프로세스 재시작뿐 → **정지+앱 재실행으로 복구**와 정확히 일치. 승자 후보: BT 경로에서 완료 콜백을 못 받은 알림음, SmartThings/Bixby TTS.
- 2순위 LoudnessEnhancer(SBS +10dB)는 예외 시 죽은 이펙트가 남는 결함이 있지만 KBS/K-POP도 조용했다는 관찰과 불일치.
- 27→13 볼륨 점프는 앱 원인 아님(앱은 명시 명령 외 볼륨을 안 만짐; 15단계 변환 가역). 사운드바 AVRCP 절대볼륨 동기화로 추정.

**확정 방법**: `adb logcat | grep -E "MediaFocusControl|PlaybackActivityMon|DuckingManager"` 에서 `ducking player piid` 뒤 `unducking` 없음; 조용할 때 `dumpsys audio`의 Audio Focus stack에 우리 위의 `GAIN_TRANSIENT_MAY_DUCK` 보유자.

**수정 방향**
1. 즉효·저위험: 채널 전환·재개 직전 `player.stop()`(IDLE→abandon) 후 prepare/play → 시스템 unduck + 배율 리셋.
2. 근본: `handleAudioFocus=false` + 서비스가 포커스 직접 관리(재생·채널 전환마다 요청, stop 시 abandon, GAIN에 `volume=1f`, -3은 시스템에 맡김) + 8초 갱신 루프에 "포커스 상실 아님 && volume<1f → 1f 복원" 워치독과 `vol=/supp=/le=` 로그.
3. LoudnessEnhancer 예외 시 null로 두고 다음에 재생성.
- 위험: 자체 포커스 관리는 과거 BT/차량 경로 문제 재발 가능(실차 검증), TTS/내비와 겹침 가능.

## 진행 제안
rc 한 번에 1·2 모두 넣되 덕킹은 1단계(stop 선행)+로그/워치독으로 먼저 가고, 자체 포커스 관리(2단계)는 로그로 1A/1B 확정 후. 태블릿 연결 시: 재현 로그 수집 → rc 설치 → 화면 꺼진 상태 2~3시간 뒤 ST 켜기 실측.
